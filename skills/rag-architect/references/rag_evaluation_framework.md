# RAG 评估框架

## 概述

评估检索增强生成（RAG）系统需要一套兼顾检索质量与生成性能的综合方法。本框架提供了覆盖流水线各阶段的 RAG 系统化评估方法、指标和工具。

## 评估维度

### 1. 检索质量（信息检索指标）

**Precision@K**：检索到的文档中相关文档的占比
- 公式：`Precision@K = Relevant Retrieved@K / K`
- 使用场景：度量不同截断点上的结果质量
- 目标值：K=1 时 >0.7，K=5 时 >0.5，K=10 时 >0.3

**Recall@K**：相关文档中被检索到的占比
- 公式：`Recall@K = Relevant Retrieved@K / Total Relevant`
- 使用场景：度量相关信息的覆盖度
- 目标值：K=10 时 >0.8，K=20 时 >0.9

**平均倒数排名（MRR）**：首个相关结果倒数排名的平均值
- 公式：`MRR = (1/Q) × Σ(1/rank_i)`，其中 rank_i 为首个相关结果的位置
- 使用场景：度量用户找到相关信息的速度
- 目标值：良好系统 >0.6，优秀系统 >0.8

**归一化折损累计增益（NDCG@K）**：位置感知的相关性指标
- 公式：`NDCG@K = DCG@K / IDCG@K`
- 使用场景：惩罚相关文档在排名中出现得靠后的情况
- 目标值：K=5 时 >0.7，K=10 时 >0.6

### 2. 生成质量（RAG 专用指标）

**Faithfulness（忠实度）**：生成的回答与检索到的上下文的贴合程度
- 度量方式：基于 NLI 的蕴含打分、事实验证
- 实现方式：检查回答中的每条论断是否得到上下文支持
- 目标值：事实型系统 >0.95，一般应用 >0.85

**回答相关性（Answer Relevance）**：生成的回答对原始问题的针对程度
- 度量方式：问题与回答之间的语义相似度
- 实现方式：embedding 相似度、关键词重合度、LLM 作为评审（LLM-as-judge）
- 目标值：聚焦型回答 >0.8，全面型回答 >0.7

**上下文相关性（Context Relevance）**：检索到的上下文与问题的相关程度
- 度量方式：对每个检索到的块进行相关性打分
- 实现方式：问题-上下文相似度、人工标注
- 目标值：top-5 块的平均相关性 >0.7

**上下文精确率（Context Precision）**：检索到的上下文中相关句子的占比
- 度量方式：句子级相关性标注
- 实现方式：对每个句子的相关性做二分类
- 目标值：高效利用上下文时 >0.6

**上下文召回（Context Recall）**：回答问题所需信息的覆盖度
- 度量方式：上下文中是否包含所有必需事实
- 实现方式：专家标注或自动化事实抽取
- 目标值：全面覆盖时 >0.8

### 3. 端到端质量

**正确性（Correctness）**：生成回答的事实准确性
- 度量方式：专家评估、自动化事实核查
- 实现方式：与参考答案对比、验证论断
- 打分：二值（正确/错误）或分档（1-5）

**完整性（Completeness）**：回答是否覆盖问题的所有方面
- 度量方式：对问题组成部分的覆盖情况
- 实现方式：基于方面的评估、专家标注
- 打分：问题方面被覆盖的比例

**有用性（Helpfulness）**：响应对用户的整体效用
- 度量方式：用户评分、任务完成率
- 实现方式：人工评估、A/B 测试
- 打分：1-5 李克特量表或点赞/点踩

## 评估方法

### 1. 离线评估

**数据集要求**：
- 多样化的查询集（统计显著性需 100+ 查询）
- 参考答案的相关性判定
- 参考回答（用于生成评估）
- 有代表性的文档语料

**评估流水线**：
1. 查询处理：标准化查询格式与预处理
2. 检索执行：以一致参数运行检索
3. 生成执行：使用检索到的上下文生成回答
4. 指标计算：计算所有相关指标
5. 统计分析：显著性检验、置信区间

**最佳实践**：
- 按类型分层查询（事实型、分析型、对话型）
- 纳入边界情况（含糊查询、无答案情形）
- 使用多名标注者并进行标注者间一致性分析
- 随系统演进定期重新评估

### 2. 在线评估（A/B 测试）

**需跟踪的指标**：
- 用户参与度：点击率、页面停留时间
- 用户满意度：显式评分、隐式反馈
- 任务完成度：特定用户目标的成功率
- 系统性能：延迟、错误率

**实验设计**：
- 随机分配到实验组/对照组
- 足够的样本量（通常每组 1000+ 用户）
- 运行时长（结果稳定需 1-4 周）
- 恰当的随机化与偏差缓解

### 3. 人工评估

**评估方面**：
- 事实准确性：信息是否正确？
- 相关性：回答是否针对问题？
- 完整性：是否覆盖所有方面？
- 清晰度：回答是否易于理解？
- 简洁性：回答是否详略得当？

**标注指南**：
- 清晰的评分细则（如带示例的 1-5 分量表）
- 每个样本多名标注者（通常 3-5 人）
- 培训与校准会议
- 定期质量检查与标注者间一致性

## 实施框架

### 1. 自动化评估流水线

```python
class RAGEvaluator:
    def __init__(self, retriever, generator, metrics_config):
        self.retriever = retriever
        self.generator = generator
        self.metrics = self._initialize_metrics(metrics_config)
    
    def evaluate_query(self, query, ground_truth):
        # Retrieval evaluation
        retrieved_docs = self.retriever.search(query)
        retrieval_metrics = self.evaluate_retrieval(
            retrieved_docs, ground_truth['relevant_docs']
        )
        
        # Generation evaluation
        generated_answer = self.generator.generate(query, retrieved_docs)
        generation_metrics = self.evaluate_generation(
            query, generated_answer, retrieved_docs, ground_truth['answer']
        )
        
        return {**retrieval_metrics, **generation_metrics}
```

### 3. 评估数据集构建

**查询收集策略**：
1. **用户日志分析**：从生产系统提取真实用户查询
2. **专家生成**：领域专家创建有代表性的查询
3. **合成生成**：基于文档内容由 LLM 生成查询
4. **社区征集**：众包方式收集查询

**参考答案构建**：
1. **文档相关性**：专家标注每个查询的相关文档
2. **答案编写**：专家撰写参考答案
3. **方面标注**：标记复杂问题的哪些方面被回答覆盖
4. **质量控制**：多名标注者并解决分歧

## 评估数据集与基准

### 1. 通用领域基准

**MS MARCO**：大规模阅读理解数据集
- 来自必应搜索的 10 万真实用户查询
- 支持段落级和文档级评估
- 同时支持检索和生成评估

**Natural Questions**：带维基百科答案的谷歌搜索查询
- 30.7 万训练样本，8 千开发样本
- 来自真实用户的自然语言问题
- 支持短答案和长答案评估

**SQUAD 2.0**：含不可回答问题的阅读理解
- 15 万问答对
- 包含无法从上下文回答的问题
- 测试系统识别不可回答查询的能力

### 2. 领域专用基准

**TREC-COVID**：科学文献搜索
- 50 个关于新冠研究主题的查询
- 17.1 万篇科学论文作为语料
- 专家相关性判定

**FiQA**：金融问答
- 648 个来自金融论坛的问题
- 5.7 万条金融论坛帖子作为语料
- 领域专用术语和概念

**BioASQ**：生物医学语义索引与问答
- 3 千个生物医学问题
- PubMed 摘要作为语料
- 专业医师标注

### 3. 多语言基准

**Mr. TyDi**：多语言问答
- 11 种语言，包括阿拉伯语、孟加拉语、韩语
- 每种语言的维基百科段落
- 文化与语言多样性测试

**MLQA**：跨语言问答
- 一种语言提问，另一种语言作答
- 7 种语言的全部两两组合
- 测试多语言检索能力

## 最佳实践

### 1. 评估设计

**指标选择**：
- 选择与业务目标对齐的指标
- 使用多个互补指标
- 兼顾自动化评估与人工评估
- 权衡计算成本与洞察价值

**数据集准备**：
- 确保查询分布有代表性
- 纳入边界情况和失败模式
- 维持高标注质量
- 定期更新和校验数据集

### 2. 统计严谨性

**样本量**：
- 基础评估至少 100 个查询
- 稳健的统计分析需 1000+ 查询
- A/B 测试需做功效分析
- 报告置信区间

**显著性检验**：
- 使用恰当的统计检验（t 检验、Mann-Whitney U）
- 多重比较校正（Bonferroni、FDR）
- 在报告 p 值的同时报告效应量
- 用自助法（bootstrap）置信区间保证稳定性

### 3. 运维整合

**自动化流水线**：
- 与持续集成/持续部署整合
- 自动化回归测试
- 性能阈值强制执行
- 质量退化告警系统

**人在回路**：
- 定期专家审查流程
- 用户反馈收集与分析
- 标注质量控制
- 偏差检测与缓解

## 常见陷阱与解决方案

### 1. 评估偏差

**问题**：测试集不能代表生产查询
**解决方案**：持续用生产数据更新测试集

**问题**：相关性判定中的标注者偏差
**解决方案**：多名标注者、清晰的指南、偏差培训

### 2. 指标博弈

**问题**：为指标优化而非为用户满意度优化
**解决方案**：多个互补指标、定期校验指标有效性

**问题**：过拟合评估集
**解决方案**：保留验证集、按时间切分

### 3. 规模挑战

**问题**：评估在规模化后过于昂贵
**解决方案**：抽样策略、自动化指标、高效工具

**问题**：人工评估成为瓶颈
**解决方案**：标注环节引入主动学习、用 LLM 作为评审做校验

## 结论

有效的 RAG 评估需要一套多维度方法，将自动化指标、人工判断和持续监控结合起来。核心原则是：

1. **全面覆盖**：评估流水线的所有组件
2. **多元视角**：结合不同的评估方法
3. **持续改进**：定期评估与迭代
4. **业务对齐**：指标应反映实际用户价值
5. **统计严谨**：恰当的实验设计与分析

本框架为构建稳健、高质量的 RAG 系统奠定了基础，使系统在保持可靠性和可信度的同时，为用户交付真实价值。
