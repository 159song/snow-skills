# 分块策略对比

## 摘要

文档分块（chunking）是高效 RAG 系统的基础。本分析在语义连贯性、边界质量、处理速度和实现复杂度等关键指标上，对比了五种主要的分块策略。

## 被分析的策略

### 1. 固定大小分块（Fixed-Size Chunking）

**方法**：将文档切分为预设大小（字符/token 数）的块，可选重叠（overlap）。

**变体**：
- 按字符：512、1024、2048 字符
- 按 token：128、256、512 token
- 重叠比例：0%、10%、20%

**性能指标**：
- 处理速度：⭐⭐⭐⭐⭐（最快）
- 边界质量：⭐⭐（差——会在句子中间截断）
- 语义连贯性：⭐⭐（低——忽略内容结构）
- 实现难度：⭐⭐⭐⭐⭐（最简单）
- 内存效率：⭐⭐⭐⭐⭐（大小可预测）

**适用场景**：
- 速度至关重要的大规模处理
- 文档类型统一
- 需要保持块大小一致

**避免场景**：
- 文档质量差异显著
- 保留上下文至关重要
- 处理叙事类或技术类内容

### 2. 基于句子的分块（Sentence-Based Chunking）

**方法**：将完整句子分组，直至达到大小阈值，确保自然的语言边界。

**实现细节**：
- 使用正则模式或 NLP 库进行句子检测
- 大小上限：通常 500-1500 字符
- 重叠：保留 1-2 个句子以保持上下文

**性能指标**：
- 处理速度：⭐⭐⭐⭐（快）
- 边界质量：⭐⭐⭐⭐（好——尊重句子边界）
- 语义连贯性：⭐⭐⭐（中等——句子之间可能主题不相关）
- 实现难度：⭐⭐⭐（中等复杂度）
- 内存效率：⭐⭐⭐（大小不定）

**适用场景**：
- 叙事类文本（文章、书籍、博客）
- 通用文本处理
- 块的可读性重要时

**避免场景**：
- 文档句子结构复杂
- 含代码/公式的技术内容
- 极短或极长句子占比过高

### 3. 基于段落的分块（Paragraph-Based Chunking）

**方法**：以段落边界作为主要切分点，并根据大小约束合并或拆分段落。

**实现细节**：
- 通过双换行符或 HTML 标签检测段落
- 大小上限：1000-3000 字符
- 对超大段落进行层级拆分

**性能指标**：
- 处理速度：⭐⭐⭐⭐（快）
- 边界质量：⭐⭐⭐⭐⭐（优秀——自然断点）
- 语义连贯性：⭐⭐⭐⭐（好——段落通常主题连贯）
- 实现难度：⭐⭐⭐（中等复杂度）
- 内存效率：⭐⭐（大小高度不定）

**适用场景**：
- 结构良好的文档
- 段落清晰的文章和报告
- 主题连贯性重要时

**避免场景**：
- 文档段落结构不一致
- 段落极长或极短
- 混合内容的技术文档

### 4. 语义分块（Semantic Chunking，标题感知）

**方法**：利用文档结构（标题、章节）和语义相似度来创建主题连贯的块。

**实现细节**：
- 标题检测（markdown、HTML 或推断）
- 通过主题建模确定章节边界
- 尊重层级的递归拆分

**性能指标**：
- 处理速度：⭐⭐（慢——需要分析）
- 边界质量：⭐⭐⭐⭐⭐（优秀——尊重文档结构）
- 语义连贯性：⭐⭐⭐⭐⭐（优秀——保持主题连贯）
- 实现难度：⭐⭐（复杂）
- 内存效率：⭐⭐（高度不定）

**适用场景**：
- 技术文档
- 学术论文
- 结构化报告
- 文档层级重要时

**避免场景**：
- 文档缺乏清晰结构
- 处理速度至关重要
- 必须将实现复杂度降到最低

### 5. 递归分块（Recursive Chunking）

**方法**：使用多种策略进行层级拆分，尽可能优先保留较大的块。

**实现细节**：
- 先尝试较大的块（章节、段落）
- 超过大小阈值时递归拆分
- 回退层级：文档 → 章节 → 段落 → 句子 → 字符

**性能指标**：
- 处理速度：⭐⭐（慢——多趟处理）
- 边界质量：⭐⭐⭐⭐（好——适配内容）
- 语义连贯性：⭐⭐⭐⭐（好——尽可能保留上下文）
- 实现难度：⭐⭐（逻辑复杂）
- 内存效率：⭐⭐⭐（优化块数量）

**适用场景**：
- 混合文档类型
- 块数量优化重要时
- 复杂文档结构

**避免场景**：
- 简单、统一的文档
- 实时处理需求
- 担心调试和维护开销

## 按领域划分的建议

### 技术文档
**首选**：语义（标题感知）
**次选**：递归
**理由**：技术文档具有清晰的层级结构，应当予以保留

### 科学论文
**首选**：语义（标题感知）
**次选**：基于段落
**理由**：论文具有章节结构（摘要、方法、结果），各章节构成连贯单元

### 新闻文章
**首选**：基于段落
**次选**：基于句子
**理由**：倒金字塔结构意味着段落通常主题连贯

### 法律文档
**首选**：基于段落
**次选**：语义
**理由**：法律文本具有特定的段落结构，不应被拆散

### 代码文档
**首选**：语义（代码感知）
**次选**：递归
**理由**：代码块、函数和类构成天然边界

### 一般网页内容
**首选**：基于句子
**次选**：基于段落
**理由**：质量和结构参差不齐，需要稳健的通用方案

## 实施指南

### 选择块大小

1. **考虑检索上下文**：较小的块（500-800 字符）利于精确检索
2. **考虑生成上下文**：较大的块（1000-2000 字符）利于生成全面的回答
3. **模型上下文限制**：确保块能放进 embedding 模型的上下文窗口
4. **查询模式**：具体查询需要较小的块，宽泛查询则受益于较大的块

### 重叠配置

- **无（0%）**：上下文渗漏造成问题时
- **低（5-10%）**：用于保持上下文连续性的通用重叠
- **中（15-20%）**：上下文保留至关重要时
- **高（25%+）**：很少有收益，且显著增加存储成本

### 元数据保留

始终保留：
- 文档来源/路径
- 块位置/序号
- 标题层级（如适用）
- 创建/修改时间戳

按需保留：
- 页码（针对 PDF）
- 章节标题
- 作者信息
- 文档类型/分类

## 评估框架

### 自动化指标

1. **块大小一致性**：块大小的标准差
2. **边界质量得分**：以完整句子结尾的块占比
3. **主题连贯性**：相邻块之间的平均余弦相似度
4. **处理速度**：每秒处理的文档数
5. **内存效率**：处理期间的峰值内存占用

### 人工评估

1. **可读性**：人能否轻松理解块内容？
2. **完整性**：块是否包含完整的思想/概念？
3. **上下文充分性**：保留的上下文是否足以支撑准确检索？
4. **边界合理性**：块边界在语义上是否合理？

### A/B 测试框架

1. **基线设置**：确立当前分块策略的性能
2. **指标选择**：选择相关指标（precision@k、用户满意度）
3. **样本量**：确保统计显著性（通常 1000+ 查询）
4. **持续时间**：运行足够长时间以覆盖使用模式
5. **分析**：统计显著性检验与实际效应量

## 成本收益分析

### 开发成本
- 固定大小：1 人日
- 基于句子：3-5 人日
- 基于段落：3-5 人日
- 语义：10-15 人日
- 递归：15-20 人日

### 运维成本
- 处理开销：语义分块比固定大小慢 3-5 倍
- 存储开销：大小不一的块可能浪费存储空间
- 维护开销：复杂策略需要更多监控

### 质量收益
- 检索准确率提升：语义分块相比固定大小提升 10-30%
- 用户满意度：更好的块边界带来可度量的提升
- 下游任务表现：更好的块可提升生成质量

## 结论

最优分块策略取决于你的具体使用场景：

- **速度至上的系统**：固定大小分块
- **通用应用**：基于句子的分块
- **高质量要求**：语义或递归分块
- **混合环境**：自适应策略选择

可以考虑实现多种策略并进行 A/B 测试，以为你的特定文档语料和用户查询确定最佳方案。
