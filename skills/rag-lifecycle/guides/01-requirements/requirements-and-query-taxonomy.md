## 概述
多数 RAG 失败不是检索算法弱，而是需求没问清：把六类查询硬塞给同一个稠密检索通道。本指南用需求八问确定系统边界，用查询分类（query taxonomy）决定每类查询走哪条检索路径，是设计期第一步。

## 需求八问

1. **文档是什么类型、多大规模？**（合同/代码/工单/ wiki；数量级决定索引与预算）
2. **查询长什么样、各占多少比例？**（要求用户给 10-20 条真实查询样例，而不是猜测）
3. **答案的精确性要求多高？**（聊天参考 vs 法律引用级，决定引用与验证深度）
4. **延迟与吞吐要求？**（P95 目标、QPS、并发）
5. **谁在什么权限下访问什么？**（单租户 or 多租户；第一天就要回答，见第 2 章数据模型）
6. **数据多久变一次？**（实时 vs 每周；决定增量索引与 as_of 语义）
7. **预算与运维约束？**（每月成本上限、可维护性、自托管倾向）
8. **合规与审计要求？**（数据驻留、留痕、可解释性）

**完成判据**：八问每问都有书面答案；没有答案的问题就是设计期最大风险，标注并让用户补齐。

## 查询分类与路由

| 查询类型 | 例子 | 检索通道 |
|---|---|---|
| **语义型（Semantic）** | "怎么处理离职交接？" | Dense 向量检索 |
| **精确型（Exact）** | "错误码 E-4021 是什么" | BM25 / 关键词 |
| **结构化型（Structured）** | "张三 2024 年的合同" | 元数据过滤 + API/SQL |
| **时序型（Temporal）** | "上季度生效的政策" | 过滤 + as_of 版本语义 |
| **多文档型（Multi-doc）** | "对比 A 和 B 方案" | 多路召回 + 归并 |
| **多跳型（Multi-hop）** | "负责该产品的人的经理是谁" | 迭代检索 / agent 路由 |

**实施要点**：
- 先用真实查询样例做人工分类，统计分布；分布决定通道优先级。
- 精确型与结构化型占高比例的语料，纯 Dense 检索必然失败——BM25 与元数据过滤从第一天就要有。
- 分类器从规则起步（关键词/正则），准确率不足再上小模型分类。
- agent 化路由的进阶做法见 [Agentic RAG 路由](../07-retrieval/agentic-rag-routing.md)。

## 何时使用本指南
- 设计期第一步：写需求 JSON（喂给 `rag_pipeline_designer.py`）之前
- 检索质量差且表现为"某类查询全错"时——先看是不是通道路由错了，而不是调参数

## 指标与成功标准
- 每类查询都有明确路由，且用 10-20 条真实样例验证过分
- 需求 JSON 的每个字段都能追溯到八问的某个答案
