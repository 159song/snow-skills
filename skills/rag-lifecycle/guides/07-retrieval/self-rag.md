## 概述
Self-RAG 是一个反思式框架：决定是否需要检索、评估被检索文档的相关性、评估回答的支撑度，并为输出有用性打分。这种动态方式根据查询特征和检索内容质量来优化检索决策。

## 问题陈述
传统 RAG 系统缺乏自省能力：
- **盲目检索**：不管是否需要都会检索
- **上下文不相关**：无法过滤掉不相关的被检索文档
- **没有依据评估**：无法核验回答是否被上下文支撑
- **策略固定**：无法适应不同查询类型
- **质量控制薄弱**：缺少评估输出有用性的机制

## 核心概念
- **检索决策**：由 LLM 判断该查询是否需要检索
- **相关性评估**：对每个被检索文档评估其与查询的相关性
- **回答生成**：仅用相关上下文生成答案
- **支撑评估**：评估回答在上下文中的扎根程度
- **有用性评分**：评估回答对原始查询的解决程度

## 实施指南

### 第 1 步：实现检索决策
用 LLM 判断查询需要检索，还是可以直接回答。

**原因**：并非所有查询都需要检索——有些可用通用知识回答，或者足够简单，检索只会增加不必要的成本和延迟。

让 LLM 做二元决策：从文档检索，或不检索直接作答。

### 第 2 步：实现相关性评估
对每个被检索文档评估其与原始查询的相关性。

**原因**：被检索文档的相关性并不均等。过滤确保只把切题的信息用于生成，降低噪声、提升答案质量。

对每个被检索文档，让 LLM 按量表评估其与查询的相关性，或分类为相关/不相关。

### 第 3 步：实现上下文过滤
构建按相关性分数过滤文档的管线。

**原因**：系统化的过滤流程保证质量一致，防止无关信息污染生成过程。

只选择达到相关性阈值的文档用于回答生成。

### 第 4 步：实现回答生成
仅用相关上下文生成回答；若无相关上下文则不用上下文作答。

**原因**：只用相关上下文能改善事实扎根。当不存在相关上下文时，系统仍可给出回答（附适当说明），而不是被迫使用无关信息。

根据是否找到相关上下文来生成回答——有则用上下文，无则用通用知识作答。

### 第 5 步：实现支撑评估
评估生成的回答被上下文支撑的程度。

**原因**：支撑评估提供置信度指标，并帮助检测幻觉——未被上下文支撑的回答可以被标记或精炼。

让 LLM 把支撑水平分类为：完全支撑、部分支撑、无支撑。

### 第 6 步：实现有用性评分
为生成的回答对原始查询的有用程度打分。

**原因**：有用性评分提供回答质量的反馈，可用于持续改进、A/B 测试或过滤低质量回答。

按回答对用户查询的解决程度打分（如 1-5 分）。

### 第 7 步：构建完整的 Self-RAG 管线
将所有组件组合成一个内聚的反思式系统。

**原因**：带清晰决策点的完整管线便于监控、优化和理解系统行为。

把检索决策、相关性评估、回答生成和各评估步骤串成统一工作流。

实现模式可参考 [Self-RAG 论文](https://arxiv.org/abs/2310.11511)、[LangGraph agentic RAG 指南](https://docs.langchain.com/oss/python/langgraph/agentic-rag)，以及 [LlamaIndex SelfRAG pack](https://docs.llamaindex.ai/en/stable/api_reference/packs/self_rag/)。

## 何时使用本 skill
- 构建回答准确率至关重要的 RAG 系统
- 查询间检索质量差异显著
- 需要置信度评分的应用
- 需要检测并处理幻觉
- 必须适应不同查询类型的系统

## 何时不使用本 skill
- 延迟极度敏感的应用（多次 LLM 调用）
- 使用的向量数据库已具备高 precision 检索
- 查询结构良好的简单 FAQ 系统
- 成本是主要约束（每次查询多次 LLM 调用）
- 有严格延迟预算的实时系统

## 指标与成功标准
- **检索效率**：不必要的检索减少 30-50%
- **相关性过滤**：识别不相关文档的 precision 高
- **回答准确率**：回答的事实扎根性提升
- **支撑置信度**：支撑评估指标可靠
- **有用性评分**：评分一致且与人工评估相关
