# 诊断 Bug（Diagnosing Bugs）

一条用于疑难 bug 的纪律。只有明确论证过理由才可跳过阶段。

探索代码库时，读 `GLOSSARY.md`（如果存在）以获得相关模块的清晰心智模型，并查你要动的区域里的 ADR。

## 脱敏

这个 skill 会让你展示命令、输出和捕获的工件。**先给每个秘密脱敏**：在原位写 `<REDACTED>`。对着环境变量搭回路，让凭据留在环境里而不是你展示的东西里。捕获的工件带 auth 头：只引用携带信号的那几行。

如果脱敏后的输出不足以诊断 bug，说明情况并向用户求助。

## 阶段 1：搭一条反馈回路

**这就是本 skill 的全部。** 其余都是机械活。如果你有为这个 bug 准备的**紧密**通过/失败信号（一条能在*这个* bug 上变红的信号），你会找到原因；二分、假设检验、插桩都只是消费它。如果没有，盯代码盯出花来也救不了你。

在这里花不成比例的力气。**要凶。要有创意。拒绝放弃。**

### 构造方法，大致按此顺序

1. 够得着 bug 的任何 seam 上的**失败测试**：单元、集成、e2e。
2. 对着运行中的 dev server 的 **curl / HTTP 脚本**。
3. 带 fixture 输入的 **CLI 调用**，stdout 与已知良好快照做 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer），驱动 UI 并对 DOM/控制台/网络断言。
5. **重放捕获的 trace。** 把真实网络请求 / payload / 事件日志存盘；隔离地穿过代码路径重放。
6. **一次性 harness。** 拉起系统的一个最小子集（一个服务、mock 掉的依赖），用一次函数调用走 bug 代码路径。
7. **性质 / fuzz 循环。** 如果 bug 是"输出有时不对"，跑 1000 个随机输入找失败模式。
8. **二分 harness。** 如果 bug 出现在两个已知状态之间（commit、数据集、版本），自动化"在状态 X 启动、检查、重复"，这样你可以 `git bisect run` 它。
9. **差分回路。** 同一输入穿过旧版本 vs 新版本（或两套配置），diff 输出。
10. **HITL bash 脚本。** 最后手段。如果必须有人来点，用 `scripts/hitl-loop.template.sh` 驱动*他们*，让回路仍然有结构。捕获的输出回流给你。

搭对反馈回路，bug 就修好了 90%。

### 拧紧回路

把回路当产品对待。有了回路*之后*，**拧紧**它：

- 能让它更快吗？（缓存 setup、跳过无关初始化、收窄测试范围。）
- 能让信号更锐利吗？（断言具体症状，不是"没崩"。）
- 能让它更确定吗？（钉死时间、种子 RNG、隔离文件系统、冻结网络。）

一条 30 秒的 flaky 回路不比没有回路好多少；一条 2 秒的确定性回路是紧的，是调试超能力。

### 非确定性 bug

目标不是干净复现，而是**更高的复现率**。把触发器循环 100 次、并行化、加压、收窄时间窗、注入 sleep。50% 的 flake 可调试；1% 不行，所以持续抬高比率直到可调试。

### 真的搭不出回路时

停下来并明说。列出你试过什么。向用户要：(a) 能复现它的那个环境的访问权，(b) 一份脱敏的捕获工件（HAR 文件、日志转储、core dump、带时间戳的录屏），或 (c) 添加临时生产插桩的许可。**不要**在没有回路的情况下进入假设。

### 完成判据：一条能变红的紧密回路

当回路**紧密**且**能变红**时阶段 1 完成：你能说出**一条命令**（一个脚本路径、一次测试调用、一个 curl），你**已经至少跑过一次**（展示该调用及其输出，脱敏），并且它：

- [ ] **能变红**：它驱动真正的 bug 代码路径并断言**用户的准确症状**，所以它能在这个 bug 上变红、修好后变绿。不是"跑起来不报错"；它必须能*抓住这个具体的 bug*。
- [ ] **确定性**：每次运行同一裁决（flaky bug：按上面的方法钉出高复现率）。
- [ ] **快**：秒级，不是分钟级。
- [ ] **agent 可运行**：你可以无人值守地跑它；人进环只通过 `scripts/hitl-loop.template.sh`。

如果你发现自己在命令存在之前就在读代码建理论，**停下：直奔假设正是本 skill 要防止的那个失败。**没有能变红的命令，就没有阶段 2。

## 阶段 2：复现 + 最小化

跑回路。看它在 bug 出现时变红。

确认：

- [ ] 回路产出的是**用户**描述的失败模式，不是碰巧在旁边的另一个失败。错的 bug = 错的修复。
- [ ] 失败跨多次运行可复现（或非确定性 bug 以足够调试的高比率可复现）。
- [ ] 你捕获了准确症状（错误消息、错误输出、慢的耗时），让后续阶段能验证修复确实对症。

### 最小化

变红之后，把复现缩到**仍会变红的最小场景**。一次砍掉一个输入、调用方、配置、数据、步骤，每砍一次重跑回路，只留对失败承重的东西。

为什么值得：最小复现缩小镇 3 的假设空间（剩下可疑的活动部件更少），并成为镇 5 里干净的回归测试。

当**剩下的每个元素都承重**时完成：去掉任何一个都会让回路变绿。

复现**并且**最小化之前不要继续。

## 阶段 3：假设

在检验任何假设之前生成 **3–5 个排序的假设**。单假设生成会锚死在第一个说得通的想法上。

每个假设必须**可证伪**：说出它做的预测。

> 格式："如果 <X> 是原因，那么 <改动 Y> 会让 bug 消失 / <改动 Z> 会让它恶化。"

说不出预测，这个假设就是玄学：丢弃或磨利它。

**检验前把排序清单展示给用户。**他们常有能瞬间重排的领域知识（"我们刚部署了对 #3 的改动"），或知道已经排除过哪些假设。便宜的检查点，大省时间。不要卡在这里等；用户挂机就按你的排序继续。

## 阶段 4：插桩

每个探针必须映射到镇 3 的一个具体预测。**一次只改一个变量。**

工具偏好：

1. 环境支持时用**调试器 / REPL 检查**。一个断点顶十条日志。
2. 在能区分假设的边界上打**定向日志**。
3. 永不"全量打日志再 grep"。

**给每条调试日志打上唯一前缀标签**，如 `[DEBUG-a4f2]`。收尾清理变成一次 grep。没标签的日志会活下来；有标签的会死。

**性能支线。** 性能退化场景，日志通常是错的工具。改为：建立基线测量（计时 harness、`performance.now()`、profiler、查询计划），然后二分。先测量，后修复。

## 阶段 5：修复 + 回归测试

**在修复之前**写回归测试，但仅当存在一个正确的 **seam**。

正确的 seam 是测试在调用现场以真实发生的方式驱动**真 bug 模式**的 seam。如果唯一可用的 seam 太浅（bug 需要多调用方却只有单调用方测试、无法复现触发 bug 调用链的单元测试），在那里的回归测试给的是虚假信心。

**不存在正确的 seam，这本身就是发现。**记下来。代码库架构在阻止这个 bug 被锁死。为下一阶段标记它。

存在正确的 seam 时：

1. 把最小化复现转成该 seam 上的一个失败测试。
2. 看它失败。如果你是通过改代码或 fixture 强行弄红的，先与干净副本 `diff` 证明改动确实落了地再信它。
3. 应用修复。
4. 看它通过。
5. 对原始（未最小化的）场景重跑镇 1 的反馈回路。

## 阶段 6：清理

宣布完成前必做：

- [ ] 原始复现不再复现（重跑镇 1 回路）
- [ ] 回归测试通过（或 seam 缺失已被记录）
- [ ] 所有 `[DEBUG-...]` 插桩已移除（`grep` 该前缀）
- [ ] 一次性原型已删除（或挪到明确标注的调试位置）
- [ ] 最终被证实的假设写进了 commit / PR message，让下一个调试者学到
