# UI 原型（UI Prototype）

在单条路由上生成**多个截然不同的 UI 变体**，通过底部悬浮栏切换。用户在浏览器里翻看变体，挑中一个（或从各变体里各偷一点），然后扔掉其余的。

如果问题关于逻辑/状态而不是东西长什么样，那就是选错了分支。用 [LOGIC.md](LOGIC.md)。

## 什么时候该用这个形态

- "这个页面应该长什么样？"
- "我想在做决定前先看几个这个 dashboard 的方案。"
- "给设置屏换一种布局试试。"
- 任何用户本来要在脑子里对着三张含糊草图纠结一整天的时候。

## 两种子形态：强烈优先子形态 A

UI 原型在**顶着真实应用环境**时远比孤立时好判断：真实的头部、真实的侧边栏、真实的数据、真实的信息密度。孤立的一次性路由是个真空：每个变体单独看都不错。只要存在一个说得通的现有页面能承载变体，就默认用子形态 A。只有当原型附近实在没有落脚点时才用子形态 B。

### 子形态 A：对现有页面做调整（首选）

路由已存在。变体渲染在**同一条路由**上，由 `?variant=` URL 查询参数门控。既有的数据获取、参数和鉴权全部保留，只换渲染部分。这是默认选择；除非有具体理由，否则选它。

如果原型针对的东西还没有页面但*自然会住在某个页面里*（dashboard 的新区块、设置屏上的新卡片、既有流程中的新步骤），它仍然算子形态 A。把变体挂载到宿主页面内部。

### 子形态 B：新页面（最后手段）

仅当被做原型的东西确实没有可以栖身的现有页面时使用（例如全新的顶层界面，或一条没法合理嵌入任何地方的流程）。

遵循项目已有的路由约定，创建一条**一次性路由**。不要发明新的顶层结构。命名要一眼看出是原型（例如在路径或文件名里含 `prototype` 一词）。同样用 `?variant=` 模式。

确定用子形态 B 之前先自检：真的没有可以嵌入的现有页面吗？空路由会藏住有内容的路由本会暴露的设计问题。

两种子形态的底部悬浮栏完全相同。

## 流程

### 1. 陈述问题并选定 N

默认 **3 个变体**。超过 5 个就不再是"截然不同"，而是噪音，所以封顶在 5。

把方案写成一行，放在原型的位置或文件顶部的注释里：

> "设置页的三个变体，通过 `?variant=` 切换，挂在现有 `/settings` 路由上。"

这样无论用户是否在场提出异议，方案都已落档。

### 2. 生成截然不同的变体

逐个起草变体。每个变体都要满足：

- 该页面的用途以及它能拿到的数据。
- 项目的组件库 / 样式体系（TailwindCSS、shadcn、MUI、纯 CSS，什么都行）。
- 清晰的导出组件名，例如 `VariantA`、`VariantB`、`VariantC`。

变体必须在**结构上不同**：不同的布局、不同的信息层级、不同的主操作方式，而不只是换个颜色。三个微调过的卡片网格不是 UI 原型，是壁纸。如果两个草稿出来太像，就带着"不许用卡片网格"的明确指令重做其中一个。

### 3. 把它们接在一起

在路由上创建单个切换器组件：

```tsx
// pseudo-code, adapt to the project's framework
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

子形态 A（现有页面）：把既有的数据获取全部保留在切换器之上；每个变体只改变被渲染的子树。

子形态 B（新页面）：`/prototype/<name>` 下的一次性路由挂载同一个切换器。

### 4. 构建悬浮切换器

屏幕底部居中一条固定定位的小栏，三个部件：

- **左箭头**：切到上一个变体（循环回绕）。
- **变体标签**：显示当前变体的 key，如果该变体导出了名字，也一并显示。例如 `B (Sidebar layout)`。
- **右箭头**：往前切（循环回绕）。

行为：

- 点击箭头更新 URL 查询参数（用框架的路由器，例如 Next 的 `router.replace`、React Router 的 `navigate` 等），这样变体可分享、刷新后不丢。
- 键盘：`←` 和 `→` 方向键也能切换。当 `<input>`、`<textarea>` 或 `[contenteditable]` 获得焦点时不要拦截方向键。
- 视觉上与页面区分开（例如高对比度药丸、轻微阴影），让人一眼看出它不属于被评估的设计。
- 生产构建中隐藏：用 `process.env.NODE_ENV !== 'production'` 或等价检查门控，这样一次走漏的原型合并也不可能把这条栏发给用户。

把切换器放进单个共享组件，让两种子形态都能复用。放在项目里共享 UI 的存放位置。

### 5. 移交

把 URL（以及 `?variant=` 的各个 key）亮给用户。用户什么时候有空就什么时候翻。有价值的反馈通常是**"我要 B 的头部配 C 的侧边栏"**——那才是他们真正想要的设计。

### 6. 归档答案并清理

一旦某个变体胜出，先归档答案（哪个变体以及为什么），再按 [SKILL](SKILL.md) 描述的方式归档原型。把胜者折入真实代码，把其余的挪到一次性分支上，不要进 main：

- **子形态 A**：把胜者折入现有页面；从 main 上撤掉落败变体和切换器。
- **子形态 B**：把胜出的变体提升为正式路由；从 main 上撤掉一次性路由和切换器。

全套变体是一手资料，所以要落在一次性分支上而不是垃圾桶，因为留在 main 分支里的变体组件和切换器烂得很快，还会迷惑下一个读者。

## 反模式

- **只有颜色或文案不同的变体。** 那是微调，不是原型。真正的变体在结构上意见相左。
- **变体之间共享太多代码。** 共享一个 `<Header>` 没问题；共享 `<Layout>` 就违背了初衷。每个变体都应该可以自由推翻布局。
- **把变体接到真实变更操作上。** 只读原型没问题。如果某个变体需要写操作，指向一个 stub：问题是"这东西应该长什么样"，不是"后端能不能用"。
- **把原型直接提升上生产。** 变体代码是在原型约束下写的（无测试、最少错误处理）。折入时请正经重写。
