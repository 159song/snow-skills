# 原型（Prototype）

原型是**用来回答一个问题的一次性代码**。问题决定形态。

## 选择分支

判断要回答的是哪个问题，依据是用户的提示词、周围代码，或者在用户在场时直接询问：

- **"这个逻辑 / 状态模型对不对？"** → [LOGIC.md](LOGIC.md)。构建单个可分享的 HTML 文件（自由操作的按钮加分页引导式走查），把状态机推入那些在纸上难以推演的场景，且非开发者也能驱动。
- **"这东西应该长什么样？"** → [UI.md](UI.md)。在单条路由上生成多个截然不同的 UI 变体，通过 URL 查询参数和底部悬浮栏切换。

两个分支产出的工件差异极大，选错了就浪费整个原型。如果问题确实含糊且联系不上用户，默认选择更契合周围代码的分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部声明这一假设。

## 两个分支通用的规则

1. **从第一天起就是一次性的，并明确标注。** 把原型代码放在它实际会被使用的地方附近（它为之做原型的模块或页面旁边），让上下文一目了然，但命名要让随意浏览的读者看出这是原型而非生产代码。对于一次性 UI 路由，遵循项目已有的路由约定；不要发明新的顶层结构。
2. **启动零门槛。** UI 原型从项目任务运行器的一条命令启动：`pnpm <name>`、`python <path>`、`bun <path>` 等。逻辑演示是用户双击即可打开的单个 HTML 文件。无论哪种，启动都不需要思考。
3. **默认不持久化。** 状态存在内存里。持久化是原型要_检验_的东西，不是它应该依赖的东西。如果问题明确涉及数据库，就动用一个临时数据库，或一个命名里带明显 "PROTOTYPE, wipe me"（原型，可抹除）字样的本地文件。
4. **跳过打磨。** 不写测试，不做超出让原型_可运行_之外的错误处理，不加抽象。重点是快速学到东西。
5. **把状态亮出来。** 每次操作（逻辑）或每次切换变体（UI）之后，打印或渲染完整的相关状态，让用户看到什么变了。
6. **完成后归档。** 把验证过的决策折入真实代码，然后把原型本身作为**一手资料**归档：提交到一个独立于 main 的一次性分支，并在实现 issue 上留下指向该分支的上下文指针。答案（结论以及它解决的问题）也要记录到 issue 或 commit 里。main 分支只保留验证过的决策。
