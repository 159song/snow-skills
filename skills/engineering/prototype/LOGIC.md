# 逻辑原型（Logic Prototype）

单个自包含的 HTML 文件（一个**可分享的演示**），让任何人都能通过点击按钮驱动一个状态模型。当问题关于**业务逻辑、状态迁移或数据形态**时使用它：这类东西在纸面上看着合理，只有推入真实场景后才会暴露不对劲。

因为它是单个文件、无需安装任何东西，你可以把它交给非开发者（设计师、PM、领域专家），让他们亲自感受这个模型。所以它要说他们的语言，而不是代码的语言。

## 什么时候该用这个形态

- "我不确定这个状态机能不能处理先 X 后 Y 的边界情况。"
- "这个数据模型真的能表示……的情况吗？"
- "我想在动手写之前先摸索一下 API 应该长什么样。"
- 任何有人想**按按钮、看状态变化**的场景。

如果问题是"这东西应该长什么样"，那就是选错了分支。用 [UI.md](UI.md)。

## 流程

### 1. 陈述问题

写代码之前，先写下你做原型针对的是什么状态模型、什么问题。一段话，放在演示顶部（可见的简介里，而不只是注释里）。回答了错误问题的逻辑原型是纯浪费，所以把问题写明确，以便日后检验——无论用户现在是否在看，还是离开了（AFK）稍后再回来。

### 2. 把逻辑隔离成可移植模块

把实际逻辑（回答问题的那一部分）放进单个 `<script>` 块，写成一个小的纯模块，日后可以被整体搬出、放进真实代码库。它周围的页面是一次性的；这个模块不是。

合适的形态取决于问题：

- **纯 reducer**：`(state, action) => state`。适合动作是离散事件、状态是单值的场景。
- **状态机**：显式的状态和迁移。适合"此刻哪些动作合法"本身就是问题一部分的场景。
- **作用于普通数据类型的一小组纯函数**。适合没有隐式"当前状态"、只有变换的场景。
- **方法面清晰的类或模块**，当逻辑确实持有持续的内部状态时。

选择最契合所问问题的形态，*而不是*最容易往页面上接线的形态。保持纯净：不碰 DOM、不碰 `document`、不让按钮处理程序伸进它内部。页面调用它；没有反向的数据流。这正是原型能超越自身生命周期的地方：问题一旦有了答案，验证过的 reducer / 状态机 / 函数集可以独立搬进真实模块。

### 3. 构建可分享的 HTML 文件

一个文件，纯 HTML/CSS/JS：无框架、无打包器、无服务器，全部内联，双击即可打开，被邮件转来转去也安然无恙。任何人打开它就能运行。

为非开发者而写。每个标签都用**领域语言**而非代码语言：按钮和状态读起来像业务，而不是 reducer。用平实的语言解释正在发生什么。

自上而下用清晰的层级排布：

1. **标题加一句话说明**，讲清这个演示让你探索什么（第 1 步的问题）。
2. **当前状态**：完整的相关状态，渲染成可读的面板（带标签的字段，而不是原始 JSON 倾倒），每次点击后重新渲染，让变化可见。在有助于非开发者跟随的地方，标出刚刚变了什么。
3. **自由操作按钮**：每个动作一个按钮，始终可用，让任何人都能以任意顺序戳这个模型。每次点击派发其动作并重新渲染状态。
4. **引导式走查**：一组**场景**，每个页签一个。每个页签有一段简短的白话场景描述（它设定的情境和要留意的点），下面是该场景按顺序**要按的按钮**。每一步都是真实按钮：点击它执行该动作并进入下一步。开始一次走查会重置到已知的初始状态，保证场景每次以同样的方式运行。

选择能演示尴尬场景的走查——那些在纸上难以推演的情况：正常路径、棘手的边界情况、一次应当非法的操作尝试。

保持美观但克制：干净的排版、宽裕的间距、一个强调色。无动画、无花招：不与状态和按钮抢注意力。

### 4. 移交

把文件发给对方，或者替他们打开。他们什么时候有空就什么时候点走查和自由操作；有意思的时刻是他们说"等等，这不应该可能"或"咦，我以为 X 会不一样"——那些是_想法_里的 bug，而这正是全部意义所在。他们想要新动作或新场景，就加。原型会演化。

### 5. 归档答案和原型

原型回答完它的问题后，先归档答案，再按 [SKILL](SKILL.md) 描述的方式归档原型。逻辑分支特有的映射：验证过的 reducer / 状态机 / 函数集搬进真实模块（决策，被吸收）；HTML 外壳随保存原型一手资料的一次性分支一起走，而且作为一个自包含文件，它在那个分支上依然随手可重跑。

## 反模式

- **不要加测试。** 需要测试的原型就不再是原型了。
- **不要接真实数据库。** 除非问题专门关于持久化，否则用内存状态。
- **不要泛化。** 不搞"万一以后要支持 X"。原型只回答一个问题。
- **不要把逻辑和页面糊在一起。** 如果纯模块引用了 DOM、`document` 或按钮处理程序，它就再也搬不动了。让页面保持为纯模块之上的一层薄壳。
- **不要伸手去够框架、打包器或服务器。** 一个接收者双击即开的文件；React 应用或 dev server 会毁掉"可分享"。
- **不要把 HTML 外壳发上生产。** 页面是为被人手工点击而优化的。它背后的逻辑模块才是值得保留的部分。
