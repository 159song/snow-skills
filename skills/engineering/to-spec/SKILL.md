这个 skill 拿当前的对话上下文和对代码库的理解，产出一份 spec。不要访谈用户；只综合你已经知道的东西。

issue tracker 和 triage 标签词汇表应该已经提供给你了。如果没有，让用户运行 `/setup-matt-pocock-skills`。

## 流程

1. 如果你还没探索过，先探索仓库以了解代码库的现状。整个 spec 使用项目的领域术语表词汇，并尊重你所触及区域内的 ADR。

2. 勾画出你要测试该特性的接缝。优先用既有接缝而不是新接缝。尽量用最高的接缝。如果需要新接缝，在你能力所及的最高点提出。代码库上跨的接缝越少越好——理想的数量是一。

与用户确认这些接缝符合他们的预期。

3. 用下面的模板写 spec，然后发布到项目 issue tracker。打上 `ready-for-agent` triage 标签——无需额外 triage。

<spec-template>

## 问题陈述（Problem Statement）

用户面临的问题，从用户的视角描述。

## 方案（Solution）

问题的解法，从用户的视角描述。

## 用户故事（User Stories）

一份很长的、编号的用户故事列表。每个用户故事的格式为：

1. 作为<角色>，我希望<功能>，以便<收益>

<user-story-example>
1. 作为手机银行客户，我希望看到我账户上的余额，以便对自己的支出做出更明智的决策
</user-story-example>

这份用户故事列表应当极为详尽，覆盖特性的所有方面。

## 实现决策（Implementation Decisions）

已做出的实现决策列表。可以包括：

- 将要构建/修改的模块
- 那些模块中将被修改的接口
- 来自开发者的技术澄清
- 架构决策
- Schema 变更
- API 契约
- 具体交互

不要包含具体的文件路径或代码片段。它们很快就会过时。

例外：如果某个原型产出了比文字更精确地编码一个决策的片段（状态机、reducer、schema、类型形状），把它内联进相关决策里，并简要注明它来自原型。裁剪到富含决策的部分，不是能跑的演示，只要重要的那几块。

## 测试决策（Testing Decisions）

已做出的测试决策列表。包括：

- 什么才是好测试的描述（只测外部行为，不测实现细节）
- 哪些模块将被测试
- 测试的先例（即代码库中类似的测试类型）

## 范围外（Out of Scope）

对本 spec 而言属于范围外的事情的描述。

## 补充说明（Further Notes）

关于该特性的任何补充说明。

</spec-template>
