# Triage（分诊）

把项目 issue tracker 上的 issue 送过一台由 triage 角色组成的小状态机。

如果本仓库把外部 pull request 当作请求面处理（见 issue-tracker 配置），triage 也覆盖它们：**PR 是一个附带代码的 issue**，用同样的角色、同样的状态、同样的状态机，下面少数几处差异标了「针对 PR」。裸的 `#42` 按 tracker 配置解析为 issue 或 PR。

triage 期间发到 issue tracker 的每条评论或 issue **必须**以这段免责声明开头：

```
> *This was generated by AI during triage.*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md)：如何写耐久的 agent 简报
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)：`.out-of-scope/` 知识库如何运作

## 角色

两个**类别**角色：

- `bug`：有东西坏了
- `enhancement`：新功能或改进

五个**状态**角色：

- `needs-triage`：维护者需要评估
- `needs-info`：等待报告者补充信息
- `ready-for-agent`：规格完整，可交给 AFK agent
- `ready-for-human`：需要人工实现
- `wontfix`：不会处理

针对 PR，同样的状态对照附带的代码来读：`ready-for-agent` 意味着简报已附上、应该由 agent 在这个 diff 上走下一步；`ready-for-human` 意味着可以交给人工合并了。

每个被 triage 过的 issue 应恰好带一个类别角色和一个状态角色。如果状态角色冲突，先标出来问维护者，再做任何别的事。

这些是规范化的角色名。issue tracker 里实际使用的标签字符串可能不同。映射应该已经提供给你了。如果没有，让用户运行 `/setup-matt-pocock-skills`。

状态迁移：未打标签的 issue 通常先进 `needs-triage`；从那里进入 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。报告者回复后，`needs-info` 回到 `needs-triage`。维护者随时可以推翻；看起来异常的迁移要先标出来问过再继续。

## 调用

维护者调用 `/triage` 并用自然语言描述想要什么。解读请求并行动。示例：

- "给我看看所有需要我注意的"
- "我们来看看 #42"（issue 或 PR）
- "把 #42 移到 ready-for-agent"
- "有什么是 agent 可以捡起来做的？"

## 展示需要关注的东西

查询 issue tracker，呈现三个桶，最旧的在前：

1. **未打标签**：从未 triage 过。
2. **`needs-triage`**：评估进行中。
3. **报告者在上次 triage 笔记之后有活动的 `needs-info`**：需要重新评估。

PR 在范围内时，把外部 PR 也纳入这些桶，并给每行打上 `[PR]` 或 `[issue]` 标记。发现面只呈现*外部* PR（tracker 配置定义了谁算外部），所以协作者进行中的 PR 不是 triage 工作。这个过滤器只用于发现；被点名的 PR 无论作者是谁一律 triage。

显示数量和每项的一行摘要。让维护者挑。

## Triage 一个具体的 issue 或 PR

1. **收集上下文。** 读完整的 issue 或 PR（正文、评论、标签、作者、日期；PR 还要读 diff）。解析之前的 triage 笔记，避免重问已解决的问题。用项目的领域术语表探索代码库，尊重该区域内的 ADR。对代码库跑两项检查：(a) **冗余**：按领域概念（而不只是请求的措辞）搜索被请求行为是否已有实现，并报告你查过哪里。如果找到，它是一个已实现的 `wontfix`（第 5 步）。(b) **此前被拒**：读 `.out-of-scope/*.md`，把任何与这个请求相似的摆出来。

2. **给建议。** 告诉维护者你的类别和状态建议及理由，外加与请求相关的简短代码库摘要（包括是否已实现）。等待指示。

3. **验证主张。** 任何拷问之前，先检查主张站不站得住。对 bug，按报告者的步骤复现。对 PR，确认 diff 做了它声称的事：check out、跑相关测试或命令。报告结果：已确认（附代码路径）、失败、或细节不足（强烈的 `needs-info` 信号）。一次确认过的验证能产出强得多的 agent 简报。

4. **拷问（如果需要）。** 如果请求需要充实，调用 Skill 工具两次，分别加载 "grilling" 和 "domain-modeling"，一轮一轮问题地把它拷问成形，随决策落定同步打磨领域术语并就地更新 `GLOSSARY.md`/ADR。

5. **应用结果：**
   - `ready-for-agent`：发一条 agent 简报评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human`：与 agent 简报同结构，但注明为什么不能委托（判断题、外部访问、设计决策、手工测试）。
   - `needs-info`：发 triage 笔记（模板在下面）。
   - `wontfix` 时，关闭 issue，评论内容取决于_为什么_：
     - **已实现**：代码库里已存在这个改动。指出它在哪；**不要**写入 `.out-of-scope/`（那个知识库是给*被拒绝*的请求的，不是给已建成的）。
     - **被拒（bug）**：礼貌地解释，然后关闭。
     - **被拒（enhancement）**：写入 `.out-of-scope/`，从评论链接过去，然后关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage`：应用该角色。有部分进展时可发可选评论。

## 快速状态覆盖

如果维护者说"把 #42 移到 ready-for-agent"，相信他们，直接应用角色。确认你将要做的事（角色变更、评论、关闭），然后行动。跳过拷问。如果是未经拷问就移到 `ready-for-agent`，问他们要不要写一份 agent 简报。

## Needs-info 模板

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

把拷问期间解决的一切收进 "established so far"，让这些工作不白费。问题必须具体可行动，不能是"请提供更多信息"。

## 恢复上一次会话

如果 issue 或 PR 上存在先前的 triage 笔记，读它们，检查报告者是否回答了任何悬而未决的问题，并在继续之前呈现更新的图景。不要重问已解决的问题。
