# 测试驱动开发（Test-Driven Development）

TDD 就是 红 → 绿 循环。本 skill 是让这个循环产出值得保留的测试的参考：什么是好测试、测试放哪里、反模式、以及循环的规则。每一节在每一轮都适用：在循环之前和之中查阅它们，而不是事后。

探索代码库时，读一下 `GLOSSARY.md`（如果存在），让测试名和接口词汇与项目的领域语言一致，并尊重你所触及区域内的 ADR。

## 什么是好测试

测试通过公共接口验证行为，而不是实现细节。代码可以彻底重写；测试不应该。好测试读起来像规格说明："user can checkout with valid cart"（用户可以用有效购物车结账）准确地告诉你存在什么能力，而且它能在重构后幸存，因为它不关心内部结构。

示例见 [tests.md](tests.md)，mock 指南见 [mocking.md](mocking.md)。

## 接缝（Seams）：测试放在哪里

**接缝**是你测试所处的公共边界：在不伸进内部的情况下观察行为的接口。测试住在接缝上，绝不针对内部。

**只在预先约定好的接缝上测试。** 写任何测试之前，先写下受测的接缝并与用户确认。未确认的接缝上一个测试都不写。你不可能测所有东西，所以预先约定接缝正是让测试投入落在关键路径和复杂逻辑上、而不是每个边角案例上的方法。

问："公共接口是什么，我们应该测哪些接缝？"给每个提议的接缝加一行说明：它能抓住什么、抓不住什么。

当接口本身的形态还在疑问中（模块该多深、接缝该放哪、接口该暴露什么）时，调用 Skill 工具加载 "codebase-design" 获取词汇。它是模块、接口、深度、接缝、适配器、杠杆和局部性这些术语的共同出处，是供查阅的参考，不是要运行的会话。

## 反模式

- **耦合实现**：mock 内部协作对象、测试私有方法、或通过旁路验证（查数据库而不是用接口）。特征：重构后行为没变，测试却挂了。
- **同义反复**：断言用与代码相同的方式重算期望值（`expect(add(a, b)).toBe(a + b)`、用同样方式手工推导的快照、断言常量等于它自己），于是它构造上就通过，永远不会与代码不一致。期望值必须来自独立的真相来源：一个已知正确的字面量、一个算出来的例子、规格。
- **横向切片**：先写完所有测试，再写所有实现。成批的测试验证的是_想象中的_行为：你测的是东西的_形状_而不是面向用户的行为，测试对真实变化变得不敏感，而且你还没理解实现就先锁死了测试结构。改用**垂直切片**：一个测试 → 一段实现 → 重复，每个测试都是一颗响应上一轮所学、随打随调的**曳光弹（tracer bullet）**。

## 循环的规则

- **先红后绿。** 先写失败的测试，然后只写刚好让它通过的代码。不要预判未来的测试，不要加投机性功能。
- **一次一片。** 每轮一个接缝、一个测试、一段最小实现。
- **重构不属于这个循环。** 它属于审查阶段（见 `code-review` skill），不属于 红 → 绿 的实现循环。
