用户要求做一次**复盘（retrospective）**。你要为编码 agent 的**环境**提出改进建议，以改善未来的运行。

## 步骤

1. 调用 Skill 工具加载 `writing-for-agents`，获取写作风格指南。

2. 阅读用户指定会话的一手资料。这可能意味着在这台机器上翻找会话日志。如果用户没有指定会话，默认用当前这个。

3. 在以下类别中寻找改进候选项。

- **导航**：agent 找到正确文件有多容易？文件之间有没有隐藏依赖？加一个**导航指针**会不会更容易？_使用时机_：会话花了很长时间才找到某条信息。
- **自动化检查**：有没有能抓住 agent 所犯错误的自动化检查？Lint、类型检查、测试、文件系统 linter？先读仓库自己的检查命令（它的 `package.json`/构建工具的 `lint`/`check` 脚本、它的 CI workflow），这样"已存在但没接线或静默损坏的检查"才是发现，而不是重新发明。一个没有**护栏**（既没有 pre-commit hook，也没有跑 lint/typecheck/test 命令的 CI job）的仓库本身就是一条发现：一个不做 lint 的仓库是长期坐失的机会，不是中性默认。_使用时机_：agent 犯了自动化检查本可抓住的错误，或者仓库根本没有护栏。
- **编码规范**：该给**审查 agent** 加一条要强制执行的新规则吗？该移除或澄清某条既有规则吗？先给违规分类：**机械性**违规（固定的语法模式、被禁的 API、import 形态、文件位置规则）直接配确定性检查，没有商量：在仓库自己的 linter 里写自定义规则、加一个 pre-commit hook、或加一个 CI job，哪个在仓库的语言和既有护栏下成本最低就选哪个。默认构建检查而不是书写规则。把 `CODING_STANDARDS.md` 留给真正的**判断题**（跨文件一致性、"与周围风格一致"，任何护栏都替代不了的东西）。_使用时机_：审查 agent 未能抓住某个错误。
- **全局 AGENTS.md**：有没有应该移入编码规范（或自动化检查）的引导指令？_使用时机_：AGENTS.md 文件特别大——无论在仓库里还是用户的全局作用域。
- **工具经济**：agent 是否做了可以精简的昂贵工具调用？有没有特别费 token 的自定义工具（CLI、MCP）？_使用时机_：agent 做了一次昂贵的工具调用。
- **空转指令**：寻找引导文件里不会改变 agent 行为的指令。_使用时机_：引导文件又大又笨重。
- **信息获取**：寻找扩大 agent 信息获取面的机会。Tee 开发服务器日志、第三方服务的只读访问。_使用时机_：某条关键信息 agent 拿不到。

4. 按严重程度排序，把这些候选项呈现给用户。

## 参考

### 实现与审查

记住所有工作都经过两个阶段：实现和审查。实现 agent 的**上下文压力**最大。它负责探索、写代码和调试失败。

审查 agent 的上下文压力最小——它拿到的是 diff，无需探索，通常也不需要写代码或调试。

这意味着应该由审查 agent 而不是实现 agent 负责强制执行编码规范。

### 文件

你可以访问仓库里的若干文件：

- `CLAUDE.md`/`AGENTS.md`：这些文件会被推送到任何在此仓库工作的 agent 的上下文窗口。应当极其克制地使用，通常只用于指向其他文件的**导航指针**。
- `CODING_STANDARDS.md`：这个文件在审查而非实现阶段被读取。如果规范文件超过 1000 行，加上指向 docs 目录的**导航指针**。
- Docs：把 docs 当作被其他文件指向的参考资料。写新文档前先找已有文档。
- Skills：用 skills 承载文档（因为它们的 description 会进入 agent 的上下文窗口），或承载用户调用的命令。遵循 `writing-for-agents` skill 中的建议。
