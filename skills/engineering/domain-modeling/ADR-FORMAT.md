# ADR 格式

ADR 放在 `docs/adr/`，使用顺序编号：`0001-slug.md`、`0002-slug.md` 等。

惰性创建 `docs/adr/` 目录：只在第一个 ADR 需要时创建。

## 模板

```md
# {Short title of the decision}

{1-3 sentences: what's the context, what did we decide, and why.}
```

就这样。一个 ADR 可以只有一段。价值在于记录*做出了*一个决策以及*为什么*，而不在于填满小节。

## 可选小节

只有真正增加价值时才包含。大多数 ADR 用不上。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：决策会被重新审视时有用
- **Considered Options**：仅当被否决的备选值得记住时
- **Consequences**：仅当非显而易见的下游影响需要点名时

## 编号

扫 `docs/adr/` 取现有最大编号并加一。

## 何时提议 ADR

以下三条必须全真：

1. **难以逆转**：之后改主意的成本可观
2. **没有上下文会让人惊讶**：未来的读者会看着代码问"他们到底为什么这么做？"
3. **真实权衡的结果**：存在真实的备选，你出于具体理由选了其中一个

决策容易逆转，跳过它：到时逆转它就是了。不惊讶，没人会问为什么。没有真实备选，除了"我们做了显然的事"没什么可记的。

### 什么算数

- **架构形状。**"我们用 monorepo。""写模型是 event-sourced 的，读模型投影进 Postgres。"
- **上下文之间的集成模式。**"Ordering 和 Billing 通过领域事件通信，不是同步 HTTP。"
- **带锁定的技术选型。** 数据库、消息总线、认证提供方、部署目标。不是每个库：只是那些换掉要花一个季度的。
- **边界与范围决策。**"客户数据归 Customer 上下文所有；其他上下文仅按 ID 引用。"显式的"不"和"是"一样值钱。
- **对显然路径的刻意偏离。**"我们因为 X 用手写 SQL 而不是 ORM。"任何合理读者会假设相反的东西。这些能阻止下一个工程师去"修"一个刻意为之的东西。
- **代码里看不见的约束。**"因为合规要求我们不能用 AWS。""因为合作方 API 合同，响应时间必须低于 200ms。"
- **否决原因不显而易见的落选备选。** 如果你考虑过 GraphQL、出于微妙理由选了 REST，记下来；否则六个月后有人会再提 GraphQL。
